# Сравнение реализаций заметок

Обе версии реализуют одинаковые операции и один демонстрационный сценарий. Иерархия состоит из `Note`, `TextNote`, `ReminderNote` и `ChecklistNote`. Номер в метаданных считает успешные вызовы `update()`, а не все изменения объекта.

## 1. Наследование

В Kotlin `Note` объявлен `abstract class`: его нельзя создать напрямую, но можно наследовать. Конкретные классы не помечены `open`, поэтому являются конечными.

В Swift `Note` — обычный класс, а три конкретных класса явно объявлены `final`. Вся иерархия помещена в `Notes.swift`: это позволяет скрыть её служебные методы через `fileprivate`. Остальной код проекта может создавать конкретные заметки, но не может вызвать `fileprivate`-инициализатор `Note`.

## 2. Инициализация

В Kotlin параметры конструктора наследника передаются в `Note(title, metadata)` в объявлении класса. Базовый конструктор выполняется до инициализации свойств наследника. Поэтому в конструкторе `Note` нет вызовов переопределяемых методов: собственные поля наследника ещё могут быть не готовы.

В Swift каждый наследник сначала присваивает значения своим хранимым свойствам, затем вызывает `super.init(title:metadata:)`. Например, `ReminderNote` устанавливает `text` и `status` перед вызовом базового инициализатора. UUID генерируется в базе один раз и не меняется при обновлении.

## 3. Override и super

Каждый конкретный тип переопределяет `display` и `contentDescription`. В Kotlin разрешение на переопределение `display` выражено через `open`, в Swift достаточно обычного метода класса.

В обеих версиях `super.display` формирует общий заголовок с названием, автором, закреплением и номером обновления. Наследник добавляет метку своего типа, содержимое и, для напоминания, статус. Поэтому `super` реально переиспользует общую логику.

## 4. Абстрактное поведение

В Kotlin `contentDescription()` и `normalizeContent()` объявлены `abstract`. Компилятор требует реализовать их в каждом неабстрактном наследнике.

В Swift нет `abstract class` и `abstract func`. Здесь выбран базовый метод с `preconditionFailure`: он выявляет ошибку реализации наследника вместо возврата фиктивного содержимого. Все три наследника предоставляют рабочие реализации. Прямое создание базы за пределами `Notes.swift` дополнительно ограничено её инициализатором.

Этот Swift-подход не даёт полной проверки обязательного переопределения на этапе компиляции: разработчик нового типа должен реализовать оба метода. Внутри файла иерархии базу всё ещё технически можно создать. Протокол сам по себе не превращает метод базового класса в абстрактный; отдельный протокол ради повторения уже существующего API здесь не введён.

## 5. Полиморфизм и расширение иерархии

`Notebook` хранит `MutableList<Note>` в Kotlin и `[Note]` в Swift. Отображение вызывает `display` через базовый тип, а фактическую реализацию выбирает динамическая диспетчеризация.

`ChecklistNote` отличается коллекцией пунктов и завершением отдельного пункта. Для его поддержки `Notebook` менять не требуется: новый класс предоставляет тот же API. Проверок конкретного типа заметки, приведений типов и обхода через `Any` нет. Проверка варианта `DisplayMode` в `when` относится к режиму отображения, а не к выбору поведения наследника.

## 6. Ограничение наследования и общий алгоритм

`update` реализует последовательность: подготовить название и проверить возможность обновления → вызвать `normalizeContent` → записать название и увеличить номер обновления. Неудачная проверка завершает операцию до изменения содержимого.

В Kotlin `update` и `renderedContent` конечные по умолчанию. В Swift они явно помечены `final`. Наследник может менять предусмотренный шаг нормализации, но не может заменить порядок общего алгоритма. `TextNote` и `ReminderNote` удаляют пробелы по краям текста, `ChecklistNote` делает это для каждого пункта, сохраняя его статус. Номер обновления защищён от переполнения.

## 7. Access control

В Kotlin `normalizeContent` и `renderedContent` имеют доступ `protected`: ими пользуются база и наследники, но не `Main` или `Notebook`. `title`, `metadata`, текст и статусы доступны для чтения, а их сеттеры закрыты через `private set`.

В Swift нет прямого аналога `protected`. Для служебных методов выбран `fileprivate`, а вся иерархия находится в одном файле. Это доступ всему файлу, а не только наследникам. Новый наследник с собственным шагом обновления нужно добавлять в `Notes.swift`. Если распределить классы по разным файлам, придётся расширить доступ шагов до `internal` или изменить дизайн. Для свойств используется `private(set)`: клиент может прочитать значение, но меняет его только владелец свойства.

Swift API проекта имеет уровень `internal`, поскольку это одно приложение, а не библиотека для других модулей. Служебные детали дополнительно скрыты от остальных файлов. `open` для наследования из другого модуля здесь не нужен.

## 8. Enum и связанные данные

Статус напоминания — обычный `enum` с двумя состояниями. В Swift строки для вывода получаются из `rawValue`, в Kotlin хранятся в свойстве `label`.

Swift `DisplayMode` — enum с вариантами `.full` и `.preview(maxLength: Int)`. Kotlin enum не позволяет отдельному экземпляру `Preview` хранить свой лимит, поэтому выбран `sealed interface` с `data object Full` и `data class Preview`. Закрытый набор вариантов позволяет написать исчерпывающий `switch`/`when`. Лимит находится внутри самого режима, без отдельного несвязанного аргумента.

## 9. Остальные конструкции

- **Отсутствующие значения.** Поиск и удаление возвращают `Note?`. Демонстрация использует `?.title` и Kotlin `?:` / Swift `??`. В Swift индекс удаления извлекается через `guard let`. Принудительного извлечения optional/nullable нет.
- **Условия.** `filter` и `first` принимают `(Note) -> Boolean` в Kotlin и `(Note) -> Bool` в Swift. В демонстрации используются лямбды с `it` и closures с `$0`.
- **Сортировка.** Kotlin принимает стандартный `Comparator<Note>` и использует `sortedWith`; демонстрация создаёт компаратор через `compareBy`. Swift принимает closure, отвечающий, стоит ли первый элемент перед вторым, и передаёт его в `sorted(by:)`.
- **Расширения.** `String.preview` реально используется при отображении. В обеих версиях лимит считается в Unicode code points/scalars, включая завершающие точки `...`; неположительный лимит даёт пустую строку. Kotlin использует `offsetByCodePoints`, Swift — `unicodeScalars.prefix`, поэтому surrogate pair у простого emoji не разрывается. Это не подсчёт составных графем: несколько scalars могут образовывать один видимый символ.
- **Value-модели.** Kotlin `NoteMetadata` и `ChecklistItem` — неизменяемые `data class`; изменение производится через `copy`. Swift использует `struct` и изменение копии. При увеличении номера обновления ранее полученные метаданные остаются прежними. Kotlin `data class` сам по себе не гарантирует value semantics для любых полей; здесь поля ограничены строками, числами и логическими значениями.
- **Коллекции.** Используются стандартные `filter`, `find`/`first`, `map`, `mapIndexed` и соединение строк. Сортировка не переставляет исходные заметки. Kotlin `all()` явно копирует список, Swift возвращает массив со значимой семантикой и copy-on-write. Оба снимка содержат ссылки на исходные объекты `Note`: удаление из блокнота не меняет состав снимка, но изменение самой заметки видно через обе ссылки. Пункты списка — отдельные value-модели; входной список Kotlin дополнительно копируется.

## Итог

Обе версии работают одинаково: общая логика находится в `Note`, а новые типы заметок можно добавлять без изменений в `Notebook`. В Kotlin такую иерархию проще описать благодаря `abstract` и `protected`. В Swift их нет, поэтому пришлось иначе ограничить доступ и проверять реализацию методов.
